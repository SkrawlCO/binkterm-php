## Current SSH userauth implementation

`ssh/src/SshSession.php::authenticate()` (around line 536):

- Expects `SSH_MSG_SERVICE_REQUEST` for `ssh-userauth`, sends `SERVICE_ACCEPT`, then a pre-auth banner.
- Auth loop, up to 6 `SSH_MSG_USERAUTH_REQUEST` messages:
  - `method === 'none'` → replies `USERAUTH_FAILURE` with the allowed-method name-list **`password`** only, partial-success = false.
  - `method === 'password'` → reads the password, calls `verifyPassword()` (HTTP `POST /api/auth/login`, `service=ssh`). On success sends `USERAUTH_SUCCESS` and returns the session bundle. On failure it **still** sends `USERAUTH_SUCCESS` and returns `['authenticated' => false]` so `BbsSession` can show its own login screen (deliberate fallback UX — see Item 9 recon).
  - any other method → `USERAUTH_FAILURE` advertising `password`.
- Exhausting 6 attempts → `USERAUTH_SUCCESS` + `['authenticated' => false]`.

**`publickey` is never advertised and never parsed.**

## What a real implementation needs

### 1. SSH protocol (new, security-critical)

RFC 4252 §7. Inside the auth loop, handle `method === 'publickey'`:

1. Read `boolean has_signature`, `string pubkey_algorithm`, `string pubkey_blob`.
2. **Query form** (`has_signature == false`): if the key is registered for `username`
   and the algorithm is allowed, reply `SSH_MSG_USERAUTH_PK_OK` (60) echoing
   `pubkey_algorithm` + `pubkey_blob`; else `USERAUTH_FAILURE`. Must not leak
   whether the *user* exists vs. whether the *key* is registered (return the
   same failure for both).
3. **Signature form** (`has_signature == true`): read `string signature`. Rebuild
   the exact signed blob:
   ```
   string    session_id
   byte      SSH_MSG_USERAUTH_REQUEST
   string    user_name
   string    service_name            ("ssh-connection")
   string    "publickey"
   boolean   TRUE
   string    public_key_algorithm_name
   string    public_key_blob
   ```
   Verify `signature` against `pubkey_blob` with the right primitive:
   - `ssh-ed25519`: blob is `string "ssh-ed25519" ‖ string key32`; signature blob
     is `string "ssh-ed25519" ‖ string sig64`. Verify with
     `sodium_crypto_sign_verify_detached($sig64, $signed, $key32)`. **Low risk — safe.**
   - `rsa-sha2-256` / `rsa-sha2-512`: blob is `string "ssh-rsa" ‖ mpint e ‖ mpint n`.
     Assemble a DER `SubjectPublicKeyInfo` from `e`/`n`, `openssl_pkey_get_public()`,
     then `openssl_verify($signed, $sig, $pk, OPENSSL_ALGO_SHA256|SHA512)`.
     **Medium risk** — hand-rolled DER, and `ssh-rsa` (SHA-1) must be rejected.
   - `ecdsa-sha2-nistp256`: more DER assembly. Probably skip.
4. Only after a *valid signature* do the account checks run.
5. Advertise `publickey` in the `none`/failure method-name-lists (currently `password` only),
   and keep `password` working alongside it (partial-success stays false; either method alone suffices).

**This is the part the campaign brief says not to build** — "substantial new SSH
cryptographic protocol code" and "uncertain signature verification".

### 2. Account mapping / web session issue (new)

`SshSession` has no DB handle and mints its BBS session by calling
`POST /api/auth/login` — which requires a password. Key auth needs a new
trusted path, e.g. `POST /api/auth/terminal-key-login`:

- Authenticated with `TERMINAL_REGISTRATION_SECRET` (the existing
  `X-Binkterm-Client-Token` convention — **do not invent a new trust mechanism**).
- Body: `username`, `key_fingerprint` (already verified by the daemon), `service=ssh`.
- Server re-checks the fingerprint is active for that user, that the account is
  active/not locked, then issues a session via
  `Auth::createAuthenticatedSession()` — the same authoritative account checks
  the password path uses.
- **Must not** be reachable without the terminal secret, and the secret's
  "unset / empty / published default = disabled" rule
  (`Config::terminalRegistrationSecret()`) applies.

### 3. Storage (new)

Additive migration, `ssh_authorized_keys`:

| column | notes |
|--------|-------|
| `id` | PK |
| `user_id` | FK `users(id)`, indexed |
| `key_type` | `ssh-ed25519`, `ssh-rsa`, … |
| `public_key` | base64 blob (no comment), unique |
| `fingerprint_sha256` | canonical `SHA256:<base64(sha256(blob))>` (no `=` padding), unique, indexed — the lookup key |
| `comment` | free text from the pasted line |
| `label` | user-supplied |
| `created_at`, `last_used_at`, `disabled_at` | revocation = set `disabled_at`, never hard-delete (audit) |

Duplicate handling: unique on `fingerprint_sha256`; a key already bound to
another account is rejected (mirrors `PgpKeyService::storeKey()`).

### 4. Management surface (later, not in a scaffold)

`SshAuthorizedKeyService` (`add`/`list`/`revoke`/`findByFingerprint`), an
`authorized_keys` line parser, web UI under user settings, and terminal-side
parity per the CLAUDE.md "User settings parity" rule. Model on `PgpKeyService`.

### 5. Throttle interaction

A **successful** public-key auth is not a failed password attempt — it must
**not** touch `LoginThrottle` counters. A malformed/failed publickey *signature*
should also not feed the password throttle (it is not a password guess);
if abuse is a concern, the SSH connection rate limiter
(`Terminal\ConnectionRateLimiter`, `SSH_RATE_LIMIT_*`) already covers the
pre-auth connection flood, and the 6-attempt auth-loop cap covers in-session
retries. No throttle change needed for this feature.

## If a human still wants a minimal first step

Smallest *safe* slice, in order, each independently reviewable:

1. Migration + `SshAuthorizedKeyService` + `authorized_keys` parser + canonical
   fingerprinting + unit tests. **No protocol code, no advertised method.**
2. ed25519-only signature verification in `authenticate()` behind an
   off-by-default `SSH_PUBKEY_AUTH` flag, plus the
   `/api/auth/terminal-key-login` endpoint. ed25519 keeps the crypto to one
   audited sodium call.
3. Web + terminal management UI.
4. RSA (`rsa-sha2-256/512`) support only if there is real demand — it carries
   the DER-assembly risk.

Steps 2–4 still need a human security review of the exact signed-blob byte
layout and the `USERAUTH_PK_OK` query-form information-leak behaviour before
activation.
